# FairTickets judge demo runbook

Run the entire demo live in front of the judges. Introduce one concert with limited inventory, then launch a staged bot scenario while the judges can see the requests and the backend’s response side by side. Follow one winning fan’s ticket through purchase, an above-cap resale attempt, a permitted transfer, and admission. End on the gate’s immediate decision and a short recap of what the judges just saw.

## Line up the interfaces

| Interface | What judges see first | What the presenter does there |
| --- | --- | --- |
| **Security Command Center** | Sale phase, unique eligible entries, capacity, contract address, and a short feed of actual backend decisions and alerts | Keep it beside the Attacker Console during the opening. Highlight the matching alert, then show the eligible count and draw outcome. Use the existing `/organiser` view as the starting point. |
| **Attacker Console** | One named scenario, a **Launch Attack** button, and a small table of attempts, responses, and reasons | Launch the bounded scenario against the local demo backend. Point to one repeated-entry attempt and one legitimate control row as the responses arrive. Match the responses to backend evidence using a run or attempt ID when available. The dedicated `/attack` view is proposed. |
| **Fan Portal** | The concert, Fan A’s verified entry, lottery outcome, and claim price | Open `/fan` after the draw. Claim the winning slot and keep its number visible for the remaining steps. Use the winner’s actual role if the draw selects a different account. |
| **Resale Marketplace** | The same slot, current owner, maximum permitted price, and listing status | Submit the above-cap price as the seller. Then list at the permitted price and switch to the buyer. Keep these actions in the existing fan flow if a dedicated `/resale` view is still pending. |
| **Gate Scanner** | Saved demo credentials labeled by owner and version, and a large admission result | Open `/gate` after resale closes. Reject the seller’s credential, admit the buyer, then scan the buyer’s credential again to show reuse failing. Paste or select from the tray to keep the handoff short. |

Start with the Attacker Console on the left and Command Center on the right of the same display. Increase browser zoom until someone standing behind the judges can read both decision rows. Pre-open Fan, Resale, and Gate tabs and bring each to full width when it becomes the focus. Have one presenter face the judges and tell them what to watch for before each action. The second person operates the browser and signals when the backend has confirmed the result. Put the event name and phase on every view. Once a slot is issued, keep its number visible through resale and admission.

## Put the attack scenarios in story order

| When | Scenario | Evidence to show |
| --- | --- | --- |
| **Opening live proof** | A known synthetic participant associated with repeated entry attempts. A legitimate participant submits a valid entry during the same run. | The organiser records a review alert for the repeated activity. The first eligible entry counts once, subsequent duplicates add no draw entries, and the control’s valid entry remains eligible. |
| **Opening control, if verified** | Several distinct verified demo participants share a network. | Show how many were eligible, how many were flagged for review, and how many were denied or remained unresolved. Shared Wi‑Fi gives judges a concrete case where several nearby fans can still be distinct people. |
| **Resale** | The current holder tries to list the ticket at ten times face value. | Show the contract-aware rejection reason and the absence of a live listing. Then show a compliant sale changing ownership and incrementing the ticket version. |
| **Admission** | Present the seller’s old credential. Admit the buyer with a fresh credential, then immediately present it again. | The seller’s credential fails because its version is stale. The buyer sees a clear **Admit** result, then **Already used** on the second scan. |
| **Judge follow-up** | Offer a forged or expired test credential and a live two-station race on a separate unused slot. | Show the specific rejection reason for the invalid credential. For the race, both stations present the same fresh credential and exactly one gets a confirmed admission. |

The current organiser alert panel provides review signals for repeated entries, request bursts, and repeated failed scans. The entry rule separately enforces wallet and attested-subject uniqueness. Present a repeated-entry alert as observed behavior and a duplicate rejection as enforcement. If the first entry is valid, that participant can still hold one draw entry. The alert alone establishes neither automated identity nor exclusion. Reserve claims about linked-account detection, challenges, distributed automation, and network-based decisions for scenarios with recorded backend evidence. If the team verifies a linked-account or distributed-automation scenario before judging, put it immediately after the repeated-entry example and pair it with the shared-Wi‑Fi control. Point to the signal that explains the different decisions, then show the resulting eligible counts. Move the extra scenario to Q&A if it crowds out the legitimate control or the draw.

For the split screen, freeze or highlight the matching rows when the result arrives. Use the actual reason and show a status such as **Allowed**, **Review**, or **Rejected**. A single attempt can generate a review signal and a separate rejection, so display them in separate columns. The current organiser panel groups some alerts by subject or event. When an exact attempt link is unavailable, show that grouping and correlate by the demo subject and time window. Avoid claiming exact correlation for a grouped alert.

## Three minute presentation

| Time | Screen and operator cue | Suggested narration |
| --- | --- | --- |
| **0:00–0:30** | Introduce the concert. Point to the configured ticket supply and the two labeled groups in the demo population. Show the split screen and point out where the response will appear. | “Fans compete for a fixed number of tickets. Watch what happens when one participant tries to get more chances, and whether the legitimate fans can still enter.” |
| **0:30–1:20** | Click **Launch Attack** in the Attacker Console. Highlight one duplicate response on the left and the related review alert on the right. Show the legitimate control and count the actual eligible entries. If the isolated baseline is ready, show its allocation result here. | “Here’s the activity the system flagged. Here’s the entry decision for that participant. The first valid entry counted once. The repeats added zero, and the distinct verified fan remained eligible.” |
| **1:20–1:50** | Close entry, lock and run the draw once it is ready. Open the winning fan’s view, claim the slot, and save the seller’s version 1 credential for the gate. | “This fan was allocated slot [number] and bought it at the event’s face price. Watch that slot number as ownership changes.” |
| **1:50–2:20** | Open resale. Submit the markup and pause on the rejection. List within the cap and buy as the second fan. Keep the old and current owner visible if the interface supports it. | “The contract rejected the markup. The permitted purchase transferred the same slot to another fan and changed its credential version from 1 to 2.” |
| **2:20–2:50** | Open the gate phase. Try the seller’s credential first. Present the buyer’s fresh credential and let the judges see **Admit**. Repeat the buyer’s scan and pause on **Already used**. | “The seller’s credential belongs to the previous ownership version, so the gate rejects it. The new owner can enter. Now we’ll try the buyer’s credential again.” |
| **2:50–3:00** | Leave the second scan result visible. Point to the single confirmed admission and recap the detection and allocation results from the opening. | “The repeated requests added zero entries, the resale stayed within the cap, and this ticket admitted one person.” |

Use the configured face price and supply throughout. For an edition configured at a displayed ₹3,000 face price, the above-cap example is ₹30,000. If the fixture uses dev ETH without a rupee display mapping, present the amounts in the fixture’s displayed units. Explain the role of the chain in one sentence if asked. The event contract owns entry uniqueness, draw results, payment and ownership changes, and the one-time admission state.

## Evidence judges should be able to inspect

- **Detection.** For a labeled fixture, show how many simulated abusive participants triggered a review alert out of all labeled abusive participants. Also show how many labeled legitimate participants triggered review, and separately how many were denied or left pending. Keep participant counts distinct from attempt counts. If the only live setup contains one repeated participant and one control, show those two outcomes directly.
- **Allocation.** Show the eligible-entry count before and after the repeated attempts. Report the winning count against capacity, then distinguish allocated slots from claimed tickets. A rejected duplicate leaves the entrant count unchanged. An eligible fan can still lose the draw.
- **Resale.** Show the attempted price, allowed cap, rejection reason, and then the confirmed purchase with the same slot number, new owner, and new version. The cap is the lower of face price and what the seller paid. The backend may reject during a contract check before broadcast, in which case there is a reason to inspect and no transaction hash for that attempt.
- **Admission.** A second scan after confirmation demonstrates sequential reuse. For a live race, use a separate unused slot and show two distinct scan IDs and exactly one confirmed admission. Keep a scan marked recovering while confirmation is uncertain. Treat only a confirmed admission receipt with the matching event as evidence that the gate admitted a fan.

If the baseline comparison is ready, show it at the end of the bot segment. Use two isolated seeded runs with the same participant labels, arrivals, capacity, and draw seed in the comparison harness. Show which rule differs, then compare eligible entries and tickets allocated by participant group. Label the comparison as a seeded simulation and keep the live judging edition on its own contract. With the current review-only detector, attribute any eligibility change to the enforcement rule that actually changed. If the comparison only changes alerting, compare alerts and report the resulting allocation as observed.

## Rehearsal and fallback

1. **Start with named fixture roles.** Pick the eventual seller and a distinct registered buyer without a ticket. Rehearse the phase changes on the demo clock and pre-stage the seller’s credential with an expiry that falls within the gate’s acceptance window. Create the buyer’s fresh credential near the scan. Confirm that the expired case and stale case produce distinguishable reasons.
2. **Confirm the opening evidence before rehearsing timing.** Verify that the repeated activity appears in the organiser feed and duplicate responses leave the eligible count unchanged. Use the same on-screen subject label throughout. If the Attacker Console is pending, run the prepared local fixture live in a readable terminal on the left and keep the organiser panel on the right.
3. **Rehearse the buyer handoff and scans.** Keep the slot visible while switching roles. Check that the old credential is still within its valid time range so the rejection demonstrates the ownership change. Scan the current credential, wait for admission, and repeat using a new scan ID. End with one confirmed admission event. For a live concurrency follow-up, have the spare slot and second scanner ready before the judges arrive.
4. **Keep a separate live edition ready at the next phase.** If the draw or purchase stalls, explain where it is pending. Continue the resale or gate proof on the prepared edition and point out the changed event and slot before taking the next live action. For a recovering gate scan, check or resume the same scan.
5. **Trim optional checks before trimming proofs.** If time runs short, drop the baseline comparison, camera interaction, and extra attack scenarios. Keep the live detection and legitimate control, the capped resale, and the stale-credential and single-admission outcomes.

For follow-up, keep the organiser’s contract address, chain ID and code hash within reach, along with the claim, resale, and admission receipts for the featured slot. The local demo proves the behavior of the configured edition and fixtures. Keep broader claims about production bot detection and draw randomness tied to the evidence available.
